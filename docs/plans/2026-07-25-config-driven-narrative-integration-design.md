# 七日 Demo 配置驱动叙事接入设计

## 目标

把已经完成的人物档案、世界观、四条特殊故事线与七日 35 宗案件接入正式工作台。内容作者应主要修改 JSON，不再为新增人物、材料、案件或工作日编排修改场景脚本。

## 方案比较

### 方案 A：继续扩充 CSV

优点是沿用旧关卡导演；缺点是嵌套材料、人物对白、身份属性和故事条件都很难表达，且会继续维持 CSV 案件与 JSON 案件两套事实来源。

### 方案 B：把所有内容写进一个巨大 JSON

优点是加载简单；缺点是人物、规则、案件与排程彼此耦合，后续协作、复用和校验困难。

### 方案 C：内容包清单 + 分表 JSON（采用）

`content_pack.json` 只声明本内容包使用的文件和默认战役；人物、用途、材料类型、规则、案件、工作日和故事线分别维护。`ConfigDatabase` 读取清单并统一索引；`LevelDirector` 按当前游戏日选择工作日，再解析固定剧情槽、条件候选和普通案件池。

## 数据流

1. `ConfigDatabase` 读取 `data/narrative/content_pack.json`。
2. 清单中的各 JSON 文件按稳定 `id` 建立索引，并完成跨表引用校验。
3. `CaseSequence` 启动当天时，`LevelDirector` 根据 `WorkdayState.day_number` 选择对应工作日。
4. 每个工作日配置五个槽位。剧情槽优先读取固定案件或条件候选；普通槽从指定池中按种子抽取。
5. 案件经 `get_gameplay_case()` 合并人物、用途和材料类型后进入现有 `CasePresenter`、规则评估和盖章流程。
6. 玩家决定仍由现有归档系统保存。后续剧情条件通过 `archived_cases` 查询跨日历史，因此不新增存档字段。

## 配置边界

- `people.json`：人物身份、视觉资产、声音、人格色和行政身份。
- `document_types.json`：文件底图和可显示字段布局。
- `purposes.json`：真实业务事项与承办部门。
- `rules.json`：机器可判定的材料、字段、有效期和签章规则。
- `demo_cases.json`：35 宗具体案件、对白、材料、错误和故事标签。
- `demo_workdays.json`：七天五槽编排、政策标题、随机种子和普通/剧情比例。
- `storylines.json`：四条故事线的角色、案件节点和叙事变量说明。

## 兼容与错误处理

旧 CSV 查询接口继续保留给现有测试和开发工具；正式工作台使用 JSON 内容包。内容包缺失时回退到原始本体路径。加载阶段拒绝重复 ID、悬空引用、无主申请表、无效槽位和不存在的条件案件。某个条件剧情未满足时，该槽位自动使用配置的后备案件或普通池，不让当天流程卡死。

## 验证标准

- 内容包能索引 18 人、4 条故事线、35 宗案件和 7 个工作日。
- 每天恰好 5 宗案件；全周为 24 宗 General 与 11 宗 Story。
- Day 1 仍能完成现有核心流程测试。
- 能从第 1 天推进到第 7 天，并按存档中的历史决定解析条件槽位。
- 所有人物贴图、材料底图、规则和案件引用均有效。
