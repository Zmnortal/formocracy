# 主玩法与本体式配置系统设计

## 目标

游戏以窗口审批工作为核心。玩家扮演一名中层干部，在有限的工作时间内接待排队群众、拆封材料、核验规则、作出审批决定并完成归档。主要压力来自处理速度、判断准确度、经济负担，以及后续逐步启用的政治信用系统。

## 单个案件的完整循环

1. 窗口外显示等待队伍，一次只有一名 NPC 上前。
2. NPC 将文件袋放入投递区。袋面显示申请人、申请目的和材料目录，但不显示表单正文。
3. 玩家把文件袋拖到工作台，点击或按住封口拆袋。
4. 文件袋展开一张主表单和若干证明材料。材料种类和数量由案件配置决定。
5. 玩家移动、摊开、叠放和对照材料，检查字段与适用规定。
6. 玩家必须在主表单上盖“批准”或“驳回”章。
7. 玩家将主表单和证明材料重新装回原文件袋。
8. 玩家把文件袋拖入验收区。案件立即封存且不可撤回。
9. NPC 离场，队列中的下一名 NPC 进入。

验收区不即时公布判断正误。漏盖章、遗漏材料等程序错误同样允许提交，但会进入追责记录。

## 工作日与时间压力

每个工作日有固定倒计时。时间结束后不再接待新 NPC，当前案件的具体收尾规则由关卡配置决定。处理越快，玩家在当天能够完成的案件越多，但仓促检查会提高误判概率。

暂停菜单与开发者控制台不消耗工作时间。NPC 入场、递交和离场动画应短促，并允许在开发模式下加速或跳过。

## 经济结算

每日结束后进入“工作日处理回执 / 内部日报”：

`基础日薪 + 正确案件绩效 - 审批罚款 - 生活支出 = 可支配余额`

首版需要记录以下结果：

- 正确批准
- 正确驳回
- 错误批准
- 错误驳回
- 漏盖章
- 遗漏材料
- 未完成或不完整归档

不同案件可以配置绩效和处罚金额。普通错误可在当日日报显示；敏感案件可以在若干天后通过复核通知、投诉或上级追责结算，避免玩家通过即时反馈反推答案。

生活支出首版包括房租、伙食和家庭支出。余额不足时形成欠款或剧情压力，不立即强制结束游戏。

## 政治信用预留

政治信用与金钱分开保存。首版只记录信用变化及原因，不强制影响主循环。后续可以影响岗位权限、特殊审批权、上级态度、晋升、调岗、降薪或解雇。

日报不直接显示精确信用分数，而使用“评价稳定”“受到关注”等模糊描述。数据层仍保存精确值，以支持规则和调试。

## 积木式本体配置

配置系统以可复用的领域对象和关系为中心，而不是为每个案件复制一整套嵌套数据。

### 核心对象

- `person`：人物与 NPC 身份
- `purpose`：申请目的或业务类型
- `case`：一次具体申请
- `document_type`：材料类型
- `document`：某份材料的具体实例
- `field`：材料中的可核验字段
- `rule`：审批规则
- `violation`：规则失败产生的问题
- `consequence`：绩效、罚款、信用和延迟追责
- `workday`：时间、队列、工资与生活支出

所有对象使用稳定、可读的唯一 ID。对象之间只通过 ID 建立关系。

### 关系示例

```text
PERSON-LIN --submits--> CASE-001
CASE-001 --has_purpose--> PURPOSE-COHABITATION
CASE-001 --contains--> DOCUMENT-ID-074
CASE-001 --contains--> DOCUMENT-RESIDENCE-019
CASE-001 --governed_by--> RULE-ADDRESS-MATCH
RULE-ADDRESS-MATCH --produces--> VIOLATION-ADDRESS-MISMATCH
VIOLATION-ADDRESS-MISMATCH --triggers--> CONSEQUENCE-WRONG-APPROVAL
```

### 规则推导

案件不直接保存“正确答案是驳回”。规则读取材料事实并产生违规项：

```text
身份证地址 != 居住证明地址
→ 产生 ADDRESS_MISMATCH
→ 正确决定为驳回
```

当所有强制规则均通过且必需材料齐全时，正确决定为批准。这样策划可以通过更换人物、字段值、材料组合或适用规则生成新案件，不需要修改主程序。

## 推荐的数据文件

首版继续采用 Godot 易读取、便于版本管理的 JSON：

```text
data/ontology/
  people.json
  purposes.json
  document_types.json
  rules.json
  violations.json
  consequences.json

data/cases/
  day_01_cases.json

data/levels/
  day_01.json
```

`ConfigDatabase` 负责加载、索引、引用校验和查询本体对象；`LevelDirector` 只负责读取工作日配置、生成队列和推进案件；独立的规则求值器负责检查材料事实并推导正确决定和处罚结果。

## 运行时案件状态

每次接待都从配置生成独立运行时副本，至少记录：

- 当前 NPC 与案件 ID
- 文件袋所在区域
- 是否已经拆封
- 已展开和查看的材料
- 每份材料当前所在区域
- 主表单上的印章结果
- 是否已重新装袋
- 提交时间与耗时
- 程序错误与规则判断结果

文件袋进入验收区后生成不可修改的处理记录。日报和延迟追责只读取处理记录，不再读取或修改桌面对象。

## 交互状态机

```text
NPC_ENTERING
→ NPC_WAITING
→ ENVELOPE_DELIVERED
→ ENVELOPE_ON_DESK
→ ENVELOPE_OPENED
→ REVIEWING
→ STAMPED
→ REPACKING
→ READY_FOR_VALIDATION
→ SUBMITTED
→ NPC_LEAVING
→ NEXT_CASE
```

状态机负责限制有效操作，但不替玩家纠正业务判断。例如未拆封时不能查看正文；材料未装回时仍可提交，但会记录程序错误。

## 首版实施边界

首版实现完整的单案件物理循环、本体对象加载、基础规则推导、倒计时、绩效与罚款结算。政治信用只保存和显示模糊评价；延迟追责先保留数据结构，可以用一个跨日示例验证。复杂关系网络、可视化策划编辑器和 RDF/OWL 等语义网技术不属于首版范围。
